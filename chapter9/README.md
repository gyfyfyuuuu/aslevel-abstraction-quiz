# Algorithm Challenge — Chapter 9

A static, mobile friendly quiz for Cambridge International AS & A Level Computer Science. The browser app is hosted by GitHub Pages; Supabase Auth and Postgres hold accounts, progress, answer keys, scoring and leaderboard data.

This challenge is added at `/chapter9/` so the repository's existing Abstraction quiz at the root remains intact. The site URL for Supabase authentication should end in `/REPOSITORY/chapter9/` for a project Pages site.

## Current state

The project files are ready, but the site is **not deployed** and has not been connected to a Supabase project. Accounts and quiz saving require a configured Supabase project. The supplied 30 questions and answer keys are included. No explanations were supplied, so none have been added.

### Sign-in choice

This build uses Supabase email and password authentication. Email supports account recovery; the four digit student ID is a public identifier and is never treated as a password. Enable email confirmation in Supabase Auth for a school deployment. Student IDs are generated by the database profile trigger and shown after the student registers. Names alone are not authentication credentials. Supabase Auth provides password hashing and its built in abuse protections; configure the project's rate limits and email provider before inviting a class.

## Supabase setup

1. Create a Supabase project and keep its database password private.
2. Open **SQL Editor**, paste the complete contents of `supabase/schema.sql`, and run it.
3. In **Authentication → URL Configuration**, set the Site URL to the GitHub Pages URL you will use (for example `https://USERNAME.github.io/REPOSITORY/`) and add it to Redirect URLs.
4. In **Authentication → Providers → Email**, enable email/password sign-in. For production, enable confirmation and configure an email provider; students will verify the address before they log in. Disable confirmation only for a controlled local demonstration.
5. Click **Connect** in the project dashboard (or open **Project Settings → API Keys**) and copy the Project URL plus the **publishable key** (starts with `sb_publishable_`) into `js/config.js`. The legacy `anon` key also works, but Supabase is moving to publishable keys:

   ```js
   window.APP_CONFIG = {
     supabaseUrl: "https://YOUR-PROJECT-REF.supabase.co",
     supabaseAnonKey: "sb_publishable_YOUR_PUBLIC_KEY"
   };
   ```

   Never put a `sb_secret_` or legacy `service_role` key in this repository or browser code.
6. Verify the SQL editor ran without errors. The signup trigger assigns a unique ID and creates an empty progress row. `submit_quiz_answer` validates the current question and answer inside Postgres; client code cannot write scores or read answer keys.

The project relies on the database RPC and table names in this schema. If you change the schema, update the browser calls at the same time. For a live school deployment, periodically review Supabase Auth rate limits and database logs.

## GitHub Pages deployment

1. Create a GitHub repository and push these files to its default branch. Do not commit a service-role key or real student data. The Supabase anon key is intended for a public browser app; the RLS policies and RPC permissions are the security boundary.
2. In the repository, open **Settings → Pages**.
3. Under **Build and deployment**, choose **Deploy from a branch**, select the default branch and `/ (root)`, then save.
4. Wait for GitHub Pages to publish, then copy the URL shown in Settings → Pages.
5. Set that URL as the Supabase Auth Site URL and allowed redirect URL as described above. Open the published URL over HTTPS.

For a project Pages URL, remember the trailing repository path in Supabase's redirect allowlist. Do not tell students the site is available until the Pages deployment has completed and the published URL works.

## Test with student accounts

After configuration, use two distinct email addresses and passwords:

1. Register Student A and Student B. Confirm the generated IDs are different.
2. Log in as A, refresh, log out, and log in again. Confirm the dashboard score and progress remain.
3. Answer a correct Level 1 question and check the score rises by 10 once. Submit a wrong answer or wait for timeout; confirm it awards zero and restarts the level at question 1.
4. Complete ten consecutive correct answers and confirm Level 2 becomes available. Confirm Level 3 stays locked until Level 2 is complete.
5. Try to call `submit_quiz_answer` for a wrong question number and try direct table updates from the browser; both should be rejected.
6. Complete all levels on both accounts and confirm they appear in each leaderboard, while incomplete users do not.
7. Repeat on a phone sized viewport and with network disabled to inspect error messages.

These are instructions for manual verification, not claims that the flows were run. I could not run end to end checks without a Supabase project and credentials. To clear test accounts, delete them from Supabase Authentication; the profile trigger's foreign key cascades to their progress. Do not delete student data without a backup/authorization.

## Scoring and timing notes

- Each correct response is validated and awarded by a single Postgres RPC. A row lock serializes submissions for a student's progress row; stale, duplicate, locked-level and wrong-question submissions are rejected.
- Wrong answers and timeouts reset the current level's streak and require restarting at question 1. Earlier completed levels and points remain.
- The client displays 40/90/150 second countdowns. The server checks the question start timestamp against its own clock before accepting an answer, so changing the browser clock does not extend a deadline. A refresh restarts the current question's full displayed timer and updates the server start timestamp as specified for this first version.
- `elapsed_seconds` adds server-measured question time across correct answers, failures, level restarts and refresh/resume events, capped at each question's allotted time. Time while logged out or away cannot be distinguished perfectly from a paused browser tab; the cap limits over-counting, but fastest-time ranks are approximate. Tiny page-transition/answer-submit overhead is not included.
- Leaderboards expose only display name, score, completion timestamp and elapsed seconds for completed students. Completion time is database generated; equal completion timestamps are ordered by the browser's stable sort/input order and are effectively ties.
- Student ID generation uses random four digit candidates plus a unique database constraint. A rare concurrent collision could cause one signup transaction to fail; it cannot create duplicate IDs.

## Accessibility and limitations

Keyboard focus, labels, readable mobile controls and reduced-motion preferences are supported. The interface avoids audio and uses text as well as colour for answer feedback. A teacher dashboard, classroom invite flow and automated expiry/reset tooling are not included. Configure Auth rate limits and the outbound email provider in Supabase; GitHub Pages itself cannot run trusted server code.
